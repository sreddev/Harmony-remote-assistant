Running a Harmony 600 without Logitech's servers

An assessment of whether the MyHarmony workflow can run entirely on your own machine, four ways to get there, and a simulation of the USB exchange a local tool would perform. Companion to the MyHarmony Teardown page.

Verdict

Yes, in stages. Backup, restore and IR learning can go fully local now. Editing the setup locally needs one piece reverse-engineered first.
USB side: solvedThe protocol scripts ship inside the app, and the open-source libconcord already reads and writes this remote family's config.
Transport: modernWebHID in Edge and Chrome, or hidapi from Python, Rust or Node, can reach the vendor-defined HID interface with no driver install.
Device codes: partialYour own devices can be exported now. New devices come from open IR databases or from learning with the remote itself.
Config compiler: unknownLogitech's server turns devices and activities into /cfg/usercfg. Its format is undocumented. That is the one real blocker.

The clock matters. Logitech shut down the older Harmony Remote Software service on 28 May 2025, which stranded the 900, One and 1100. The MyHarmony service your 600 uses still answered on 11 Nov 2026. While it does, it can act as an oracle: every change you make and sync shows exactly how the config bytes change.

Proposals

Four options, ranked. The first three build on each other. Ratings are judgment calls, from 1 to 5.

A · Lifeboat

Backup and restore

A small local tool that reads the remote's identity and config file and writes it back. It protects the setup you have today, permanently.

  • Single-file WebHID web page, or a Python script on hidapi
  • Uses only operations libconcord already performs
  • Refuses to restore onto a remote with a different GUID
Feasibility
Effort
days
Risk to remote
low, read first
B · Export

Account export

A one-time export of everything your account holds: devices with their IR commands, activities, button maps and sequences, saved as JSON.

  • Replays the app's own SOAP calls with your signed-in session
  • Keeps your data usable after the servers close
  • Feeds the device library in proposal C

C · Local Studio

Full local replacement

A modern desktop app with its own device library, activity and button editor, and a local compiler that writes the remote's config over USB.

  • Tauri or a WebHID web app, with SQLite storage
  • Compiler built with the Rosetta harness below
  • Works offline forever once the format is known
Feasibility
gated on format
Effort
weeks to months

medium, A undoes it
D · Replay shim

Fake the cloud for the old app

Point setup.myharmony.com at a local HTTPS server that serves cached app packages and recorded answers, so the existing MyHarmony UI keeps loading.

  • Needs a hosts-file entry and a locally trusted certificate
  • Still cannot compile new configs, so edits fail
  • Keeps a 2013 browser and Silverlight in use

Related projects

Two open-source projects checked for reuse on 11 Nov 2026.

turlvo/KuKuHarmony

No help for the 600

A SmartThings SmartApp that triggers devices through a Harmony Hub via the community harmony-api server. It controls an existing Hub setup over the network. It cannot program a remote, and the 600 has no Hub or network link.

Not applicable Relevant only if a Harmony Hub is added later.

harmonic-afterglow/afterglow

Strong reference, not a drop-in

A Python app (GPL-3.0) that builds configurations locally and writes them over USB, made after the May 2025 shutdown. It is the existence proof for proposal C. It supports the Harmony 900 (arch 15), with the One and 1100 experimental. The 600's Molson family (arch 14/16, /cfg/usercfg) is not covered.

  • Reuse the method: trace real configs, round-trip losslessly, keep unknown bytes as hex
  • Test its IR bytecode docs (IrProto.bin, SsIr.bin) against a 600 backup
  • Option: add a Molson profile to Afterglow instead of building the Studio from zero

Licensing Code built on it and shared must also be GPL-3.0.

The first Lifeboat backup decides between the two paths. If /cfg/usercfg contains Afterglow's IR container (a 6-byte prefix, a u16 block count, then u16 offsets), extending Afterglow is the shorter route. If it doesn't, the Rosetta harness is still needed and Afterglow stays a design reference.

Rosetta harness

How to learn the config format while Logitech's compiler still answers.

flowchart LR
  A["Make one small change
in MyHarmony"] --> B["Sync through
Logitech cloud"]
  B --> C["Lifeboat reads
/cfg/usercfg"]
  C --> D["Diff against
previous snapshot"]
  D --> E["Record: change
to byte regions"]
  E --> F{"Pattern clear?"}
  F -- "no" --> A
  F -- "yes" --> G["Encode the rule
in local compiler"]
  G --> H["Verify: local output
equals cloud output"]

Each round isolates one variable: rename an activity, add one device, remap one button, change a power setting. Snapshots and their change notes go into the repo. The goal is a compiler whose output matches the cloud's byte for byte on every recorded case. Until it does, the Studio can still write any config you captured earlier.

The checksum is already partly known: libconcord sends a finish message with type, seed, length and expected value, and contains an XOR-of-16-bit-words routine with seed 0x4321. That should be confirmed against a real capture.

Roadmap

  1. Week 1Lifeboat, read-only firstIdentify the remote and read /cfg/usercfg. Save the file with its SHA-256 and the identity. Do this before anything else.
  2. Week 1–2Account exportExport devices, IR commands, activities and button maps to JSON while the servers answer.
  3. Week 2Lifeboat restoreWrite the saved file back and confirm the remote still works. This proves the write path and gives a safe undo for every later step.
  4. Weeks 2–6Rosetta roundsCollect paired changes and snapshots until the main structures of the config are mapped.
  5. Weeks 6+Local StudioEditor, device library and compiler. Ship it when local output matches the recorded cloud output.
